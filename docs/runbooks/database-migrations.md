# Runbook — database migrations

Operational procedure for the `@combat/database` Prisma schema against a live
PostgreSQL instance. Established by **AAMP-1 step 1** (see
`docs/aamp-architecture.md` §6, implementation tasks 1–3).

Scope: local development and the forward-only production deployment path.
Authentication, Temporal, MinIO and backup _automation_ are later AAMP-1 steps
and are deliberately not covered here.

---

## 1. Baseline

The migration baseline is a single initial migration,
`packages/database/prisma/migrations/20260726053508_init/`, generated by
`prisma migrate dev` against a live PostgreSQL 16 instance. It covers all 50
models, 41 enums, 41 unique indexes, 76 indexes and 68 foreign keys currently in
`schema.prisma`.

`migration_lock.toml` pins the provider to `postgresql`. Do not change it.

**Migration SQL is never hand-authored** (CLAUDE.md "Migration rules"). Files
under `prisma/migrations/` are produced by Prisma and reviewed before commit.
The one narrow exception requires the reason to be documented in this runbook.
One exception has been taken: see §4.2, where `migrate diff` generated the SQL
because `migrate dev` cannot run without an interactive terminal. The SQL was
still produced by Prisma, not written by hand.

## 2. Local startup

From the repository root:

```sh
docker compose -f infrastructure/docker-compose.yml up -d postgres
```

`postgres` is the canonical Compose service name. Bring up only this service for
migration work — Temporal, MinIO and the Temporal UI are separate AAMP-1 steps
and are not required.

The image is `postgres:16-alpine` (currently resolving to PostgreSQL 16.14).
PostgreSQL 16 is the supported major for this project; the schema's DDL is
generated for it.

Credentials come from `infrastructure/docker-compose.yml`'s inline defaults,
which match `.env.example`: user `postgres`, password `postgres`, database
`combat_creative_os`. **These are local-development placeholders, not secrets.**
A real deployment supplies `DATABASE_URL` through its own secret management —
never through a committed file.

On first volume initialization, `infrastructure/postgres/init/01-create-app-db.sql`
creates the `combat_creative_os` database alongside the databases Temporal's
`auto-setup` image creates for itself on the same instance.

## 3. Health verification

```sh
docker compose -f infrastructure/docker-compose.yml ps postgres
docker inspect --format '{{.State.Health.Status}}' combat-creative-os-postgres-1
```

Expect `healthy`. The Compose health check is `pg_isready`, 5 s interval, 10
retries. Then confirm the application database actually accepts a connection —
`pg_isready` proves the server is up, not that the database exists:

```sh
docker exec combat-creative-os-postgres-1 \
  psql -U postgres -d combat_creative_os -tAc "select current_database();"
```

If startup fails, read only the relevant tail:

```sh
docker compose -f infrastructure/docker-compose.yml logs --tail=50 postgres
```

## 4. Generating a migration (development only)

After changing `schema.prisma`:

```sh
pnpm --filter @combat/database run migrate --name <short_snake_case_name>
pnpm db:generate   # regenerate the Prisma Client before typecheck/build
```

`pnpm db:migrate` is the same command without a name (Prisma will prompt).

`prisma migrate dev` is a **development-only** command. It creates and drops a
shadow database to detect drift, and it will offer to reset the database if
history and schema have diverged. Never point it at staging or production.

Review the generated SQL before committing it. Check that indexes, unique
constraints, foreign keys, enum values and `ON DELETE`/`ON UPDATE` behaviour
match the Prisma schema, and that any new workspace-owned table has a
`workspaceId` column with an index led by that column (CLAUDE.md "Migration
rules").

### 4.1 Migration directory names are ordered lexicographically

Prisma applies migrations in **directory-name order**, not creation order. On
this machine the existing chain is named from **local** time — `20260727010351`
corresponds to `15:03:51 UTC`, matching that row's `finished_at` exactly — so a
directory named from UTC sorts _before_ migrations created earlier the same day.

That is not cosmetic. During AAMP Creative Memory injection, a directory
initially named `20260726181737` (UTC) sorted ahead of
`20260727010351_add_creative_memory_reference_tables` and, on a fresh database,
ran before the enum it depends on existed:

```
Error: P3018  type "ReferenceBusinessRole[]" does not exist
```

The live database was unaffected — it already had the enum — so **only the
fresh-database replay caught it**. Always replay the complete chain into an
empty disposable database before committing a migration; a migration that only
works on a database that already exists is not a migration.

### 4.2 Documented exception — `migrate diff` + `migrate deploy`

`20260727041853_add_benchmark_governance_profiles` was **not** created by
`prisma migrate dev`. That command refuses to start without an interactive
terminal, and the agent session that produced this milestone has none.

The narrow exception CLAUDE.md's "Migration rules" allows was taken, and this is
the record of it. The SQL was still **Prisma-generated, never hand-authored**:

```sh
npx prisma migrate diff \
  --from-url "<disposable clone restored from a verified pg_dump -Fc>" \
  --to-schema-datamodel prisma/schema.prisma \
  --script > <migration dir>/migration.sql
npx prisma migrate deploy
```

Before it reached the real database it was: scanned for `DROP`/`DELETE FROM`/
`TRUNCATE`/`ALTER COLUMN`/`RENAME`/DML (zero hits — the only `DELETE` token is
the `ON DELETE SET NULL` referential action), applied and drift-checked against
a faithful clone, replayed into an empty database as part of the complete chain,
and drift-checked again. `prisma migrate status` then showed exactly one pending
migration on the real database before `migrate deploy` applied it.

Prefer `migrate dev` in a real terminal whenever one is available. Use this path
only when it is not, and record the reason here.

### 4.3 A rolled-back row is not a modified migration

`_prisma_migrations` carries one stale row for
`20260726062308_add_user_clerk_subject`: `applied_steps_count = 0`,
`finished_at` NULL, `rolled_back_at` set, logging a Postgres `42601` syntax
error at position 1 caused by a UTF-8 BOM in the first attempt. The BOM was
stripped and the migration re-applied successfully as a second row whose
checksum matches the committed file byte-for-byte.

`prisma migrate dev` reports this as _"the migration was modified after it was
applied"_ and offers to reset. **The file was never modified**, and the row was
never proven to be the cause — `migrate status`, `migrate deploy` and drift
detection all accept it, and a controlled two-clone experiment could not
distinguish its presence from its absence on any non-interactive probe.

Leave the row alone. It is inert for `status`, `deploy` and drift detection, and
deleting it would be an unproven fix to `_prisma_migrations` for a problem that
`migrate deploy` does not have.

## 5. Deploying a migration (staging and production)

```sh
prisma migrate deploy
```

`migrate deploy` applies pending migrations and nothing else: no shadow
database, no drift prompt, no reset, no generation of new migration files. It is
the only migration command permitted against staging or production.

**Back up before every production migration.** Take and _verify_ a `pg_dump`
before applying, and confirm the dump is restorable — an unverified dump is not
a backup. Automated backup scheduling and the restore drill are AAMP-1 task 8;
until that lands, the pre-migration dump is performed manually and recorded.

## 6. Drift check

Confirms the live database still matches `schema.prisma`:

```sh
cd packages/database
npx dotenv -e ../../.env -- prisma migrate diff \
  --from-schema-datasource prisma/schema.prisma \
  --to-schema-datamodel  prisma/schema.prisma \
  --exit-code
```

`No difference detected.` with exit code `0` means no drift; exit code `2` means
the database and schema disagree and must be reconciled before deploying.

Applied-state check:

```sh
cd packages/database && npx dotenv -e ../../.env -- prisma migrate status
```

Expect `Database schema is up to date!`.

## 7. Rollback and recovery

### Prisma migrations are forward-only

Prisma does not generate down migrations, and this project does not invent them.
An automatically-derived rollback script is unsafe: it cannot recover data a
destructive change discarded, and it silently diverges from what actually ran.

**Recovery from a bad migration in production is therefore one of two paths:**

1. **Forward fix (preferred).** Write a new migration that corrects the
   problem, review it, and `migrate deploy` it. This keeps history linear and
   auditable.
2. **Restore from backup.** Only when the bad migration destroyed data that a
   forward fix cannot reconstruct. Restore the pre-migration `pg_dump` into a
   scratch database, verify row counts and referential integrity, then cut over.

### Destructive schema changes use expand/contract

Never drop or retype a column in the same release that stops writing it. Expand
(add the new column, backfill, dual-write), ship, then contract (drop the old
column) in a later migration once no deployed code reads it. This keeps every
intermediate state rollback-safe by deploying the _previous application build_,
without touching the database.

### A migration that failed part-way (marked failed in `_prisma_migrations`)

Prisma refuses to proceed while a migration is recorded as failed. Resolve it
explicitly once you have determined what actually landed in the database:

```sh
# The migration's changes were NOT applied (or you reverted them by restore):
prisma migrate resolve --rolled-back <migration_name>

# The migration's changes WERE fully applied by hand and are correct:
prisma migrate resolve --applied <migration_name>
```

Marking a partially-applied migration `--applied` leaves the database in a state
the schema does not describe. Verify with the §6 drift check afterwards, every
time.

### Failed migration on a local development database

A local database is disposable, so the fastest correct path is to rebuild it:

```sh
cd packages/database
npx dotenv -e ../../.env -- prisma migrate reset   # LOCAL ONLY — see the warning below
```

This drops the database, re-applies every migration from scratch and re-runs the
seed (`prisma/seed.ts` — one workspace, one `OWNER_ADMIN` user, the membership
linking them). If you only want to discard the container's state entirely:

```sh
docker compose -f infrastructure/docker-compose.yml down -v   # deletes the postgres-data volume
```

> **`prisma migrate reset` and `docker compose down -v` are prohibited against
> staging and production.** `migrate reset` drops and recreates the database:
> against a shared environment it is unrecoverable data loss, not a repair.
> Before running either, positively identify the target — read the resolved
> `DATABASE_URL` host and database name — and confirm it is the local
> disposable development database. If the target is unresolved, stop and
> resolve it first. Production recovery is §7's forward fix or restore path,
> never a reset.

## 8. Verifying a migration is sound

Run against a live local PostgreSQL before committing:

| Check                  | Command                                                                 | Expected                            |
| ---------------------- | ----------------------------------------------------------------------- | ----------------------------------- |
| Schema valid           | `pnpm db:validate`                                                      | `The schema ... is valid`           |
| Client generates       | `pnpm db:generate`                                                      | `Generated Prisma Client`           |
| History applied        | `prisma migrate status`                                                 | `Database schema is up to date!`    |
| No drift               | §6 drift check                                                          | `No difference detected.`, exit `0` |
| Applies to an empty DB | `createdb` a scratch database, `DATABASE_URL=... prisma migrate deploy` | all migrations applied              |
| Repeatable             | re-run `pnpm --filter @combat/database run migrate`                     | `Already in sync`, no new migration |
| Package tests          | `pnpm --filter @combat/database test`                                   | pass                                |

Drop the scratch database afterwards.

Note that `packages/database`'s Vitest suite runs against the in-memory store,
not PostgreSQL — it verifies repository logic and mirrored constraints, and it
passes with or without a live database. It is not evidence that a migration
applied.
